# 말랑몰랑 — 기획 핸드오프 (Handoff Context)

이 문서는 claude.ai에서 진행된 브레인스토밍 + 기획 세션의 핵심 맥락을 기록합니다.
코드를 작성할 때 "왜 이렇게 결정했는지"를 이해하기 위한 참고 자료입니다.

---

## 프로젝트 동기

개발자 본인이 MORT(기존 Windows 화면 번역기)를 직접 사용하면서 느낀 불만에서 출발했습니다:

- **OCR 인식률**: 게임의 화려한 배경이나 특이한 폰트에서 글자를 잘못 읽음
- **번역 문체**: 직역 느낌의 어색한 번역
- **딜레이**: 반응 속도가 느림

이 중 번역 문체는 LLM을 쓰면 자연스럽게 해결되고, 딜레이는 구조적 한계(OCR+LLM)라 최적화만 가능하므로, **OCR 인식률을 LLM으로 보완하는 것**이 핵심 가치로 결정되었습니다.

---

## 핵심 설계 결정과 이유

### 1. 왜 Python + PyQt6인가?

3가지 선택지를 비교했습니다:
- **Python + PyQt6** (선택됨): 진입장벽 최저, 라이브러리 생태계 풍부, AI 코드 생성 품질 최고
- C# + WPF: Windows 네이티브로 성능은 좋지만 학습 부담
- Electron: UI는 예쁘지만 메모리 과다, 시스템 레벨 기능 구현 어려움

개발자가 Python만 약간 접해본 초보이므로 Python이 유일한 현실적 선택이었습니다.

### 2. 왜 두 가지 모드(영역 지정 + 커서 추적)인가?

개발자의 실제 사용 환경에서 나온 결정입니다:
- **듀얼 모니터** 사용자라 전체 화면 캡처(B안)는 비효율적
- **게임**: 대화창 위치가 고정적 → 영역 지정이 적합
- **웹/문서**: 텍스트가 분산되어 있음 → 커서 추적이 적합

전체 화면 캡처 모드는 명시적으로 제외되었습니다.

### 3. 왜 BYOK(Bring Your Own Key)인가?

수익화를 당장 고려하지 않으므로, 서버 운영 비용을 Zero로 유지하기 위함입니다.
나중에 수익화할 경우 "프록시 서버를 통한 구독/크레딧 모델"을 추가하는 방향으로 논의되었으나, 1차 스코프에는 포함하지 않습니다.

### 4. 왜 로컬 모델도 지원하는가?

개발자의 PC 사양이 Gemma 4 26B 양자화 모델을 20~30 tps로 돌릴 수 있을 정도로 충분합니다.
"쓸 사람은 써라" 수준의 옵션이며, Ollama의 로컬 API가 클라우드 API와 같은 인터페이스를 제공하므로 구현 비용이 낮습니다.

### 5. 왜 Vision API를 별도 경로로 추가했는가?

MORT 개발자 블로그를 조사하던 중, MORT가 이미 LLM 번역을 지원하고 있음을 발견했습니다.
다만 MORT의 LLM 연동은 단순 번역(text in → text out) 구조였습니다.

차별화를 강화하기 위해 Vision API 경로를 추가했습니다:
- **경로 A (기본)**: 캡처 → OCR → 텍스트를 LLM에 전달 (교정+번역)
- **경로 B (Vision)**: 캡처 → 이미지를 Vision LLM에 직접 전달 (인식+번역 한 번에)

OCR 오류 자체를 근본적으로 제거하는 접근이지만, API 비용이 더 높고 로컬 모델로는 어려울 수 있어 선택 옵션으로 배치했습니다.

### 6. 왜 오버레이 스타일을 자동 매칭하지 않는가?

YAGNI 원칙에 따라 1차 스코프에서 제외했습니다. 게임마다 폰트와 배경이 전부 달라 자동 매칭은 복잡도 대비 효과가 낮습니다. 대신 사용자가 프리셋을 만들어 저장하는 방식으로 대체합니다. (참고: MORT는 이미 자동 폰트/배경색 매핑을 구현하고 있음)

### 7. 번역 프로필이란?

기획 막바지에 추가된 아이디어입니다. 핵심 개념:
- **프리셋** = "어떻게 보여줄지" (폰트, 색상, 투명도)
- **프로필** = "어떻게 번역할지" (톤, 분위기, 용어집)

게임 이름을 입력하면 Steam API에서 장르/태그를 가져와 번역 톤을 자동 설정하거나,
사용자가 직접 "이건 다크 판타지 RPG야, 용어 X는 Y로 번역해줘"를 입력할 수 있습니다.
웹/문서에는 "기술 문서", "뉴스", "블로그" 등 카테고리 퀵 선택을 제공합니다.

### 8. 성능 목표는 왜 3초가 아니라 5~8초인가?

초기에 "클라우드 API 기준 3초 이내"로 잡았으나, 현실적으로 불가능하다는 피드백이 있었습니다:
- 캡처 + OCR만 ~500ms
- 경량 LLM API 호출: 최소 1~2초
- 일반 LLM: 3~5초

최종 목표:
- 경량 모델: 평균 5초 이내
- 일반 모델: 평균 7초 이내
- 로컬 모델: 평균 5~8초
- LLM 이외 구간: 1초 이내

## MORT 조사 결과 요약

MORT GitHub (https://github.com/killkimno/MORT) 및 관련 글을 조사한 결과:

**MORT가 하고 있는 것:**
- C#/.NET 기반, OCR 엔진 5종 지원 (Tesseract, Windows OCR, Google Cloud Vision, Snipping Tool OCR, EasyOCR)
- Gemini API 연동 (Temperature, Thinking Level 설정)
- Ollama 연동
- 오버레이 자동 폰트/배경색 매핑
- DB를 이용한 번역본 저장/재사용
- 커스텀 API 인터페이스 (POST: text, target, source → result)

**MORT가 안 하고 있는 것 (= 우리의 차별점):**
- OCR 오류 교정을 LLM에 지시하는 프롬프트 설계
- 이전 대사 문맥을 프롬프트에 포함하는 기능
- Vision API를 통한 OCR 단계 우회
- 커서 추적 모드
- 번역 프로필 (콘텐츠별 톤/용어/문맥 사전 정의)
- 이미지 해시 기반 변경 감지

## 스코프 우선순위

**Phase 1 (MVP):** 영역 지정 + OCR + LLM 번역 + 오버레이 + 변경 감지 + 기본 설정
**Phase 2:** 커서 추적, 사이드 패널, 캐시, 문맥 기억, Vision API, 번역 프로필(수동), 프리셋
**Phase 3:** Steam 연동, 프롬프트 커스텀, 단축키 커스텀, 다국어 UI, 자동 업데이트
